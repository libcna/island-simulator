# Asset Pipeline and Validation

## Current content model

The current game ships no external mesh, texture, animation, font, or audio files. Terrain,
vegetation, natural props, the shipwreck, wildlife meshes and animation, the sky, ocean, soundscape, touch UI,
and developer font are generated by original project code at runtime. This is an intentional
portable baseline, not permission to add untracked files later. The original Android launcher
vector is a hash-gated project file rather than an external asset or runtime generator.

`ASSET_LICENSES.md` is the human-readable provenance authority. `assets/manifest.json` is its
machine-readable gate. The manifest currently maps 19 documented procedural content systems to
36 source files, hashes two original project-owned files, and declares an empty
external-file set.

Generated build outputs, captures, APK contents, WebAssembly, shader compiler intermediates, and
runtime PCM buffers are not source assets. They remain in ignored build directories and must be
reproducible from tracked source.

## Manifest schema

`assets/manifest.json` uses schema version 2 and has three arrays:

- `proceduralGenerators` records a stable generator name, the exact first-column asset name from
  `ASSET_LICENSES.md`, and every source file that owns that generated content.
- `projectFiles` records original non-generated distributable files with a stable name,
  repository-relative path, exact SHA-256, and matching attribution row.
- `externalFiles` records every externally sourced file kept under `assets/`. Each entry requires
  `name`, repository-relative `path`, `role` (`source` or `runtime`), lowercase SHA-256, stable
  `source`, `author`, exact `license`, `modifications`, in-game `use`, and `licenseRecord`.

Every file under `assets/` except the manifest must be listed as project-owned or external.
Absolute paths and parent-directory traversal are rejected. The validator checks existence, exact
SHA-256, schema fields, duplicate paths/names, generator source files, and matching attribution
rows. Original distributable artwork outside `assets/`, such as an Android resource, must also be
listed explicitly in `projectFiles`.

## Validation commands

Validate provenance without compiling:

```bash
python3 tools/validate_assets.py
python3 tools/validate_assets.py --output /tmp/island-asset-report.json
```

Build and run the renderer-independent deterministic world report:

```bash
cmake --build build --target island_world_report --parallel 2
build/island-world-report --output /tmp/island-world-report.json
build/island-world-report > /tmp/island-world-report.json
```

Both world-report forms produce the same JSON. With `--output`, the concise validation status is
written to stdout; without it, JSON is written to stdout and status to stderr so redirection stays
machine-readable.

The report reconstructs the authoritative terrain, all placement layouts, the combined collision
grid, and initial wildlife state twice. It rejects non-finite data, invalid population envelopes,
derived-count disagreements, missing/invalid placement scale, and nondeterministic reconstruction.
It records:

- the four public layout seeds;
- sampled shoreline radius, terrain height, and surface-class populations;
- every current environment placement population, including exact shipwreck dimensions, signed
  shore distance, 12 debris pieces, and six collision proxies;
- combined obstacle and occupied-cell counts;
- initial wildlife populations, including all thirty beach crabs and their six bounded colony
  regions;
- a 64-bit fingerprint over sampled terrain and ordered generated world data.

The fingerprint is a change detector for the qualified host/toolchain, not a promise that different
standard-library math implementations produce identical floating-point bits. Intentional world
changes may change it; review the JSON diff rather than replacing it blindly.

`IslandAssetValidation`, `IslandWorldReport`, `IslandAudioReport`, and the temporary WAV-export
validator are registered with CTest on native host builds. They do not enter Web or Android
products. The standard full private-display test command also runs them before or alongside
renderer tests. Audio-specific semantics are documented in `docs/audio-review.md`.

## Adding an external asset

Before an external file enters a runtime build:

1. Confirm that its license permits source storage, redistribution, modification, and the intended
   game use. Do not use commercial-game extractions or uncertain uploads.
2. Preserve the best legal source form under `assets/`; do not make a remote URL the only copy.
3. Add an `ASSET_LICENSES.md` row with source, author, exact license, modifications, and use.
4. Add every source and runtime file to `externalFiles`, including exact SHA-256 values. Record a
   stable upstream page or archive identifier in `source`.
5. Keep conversion deterministic. Put conversion code under `tools/`, document required versions
   and options here, and keep only intermediates needed to reproduce or legally modify the asset.
6. Prefer formats and encodings that CNA already supports on OpenGL 3.3, WebGL 2, and OpenGL ES 3.
   If target-specific outputs are necessary, manifest each output and test all consumers.
7. Run asset validation, native tests, the actual browser harness, and Android packaging. Runtime
   qualification still requires visual/audio inspection on the relevant platform.

## Adding or changing procedural content

Add new generator ownership to `proceduralGenerators` and a corresponding attribution row. When an
existing generator gains another owning source, extend its `sources` list. Then run the world
report and inspect count/range/fingerprint changes. A count change is not automatically a failure,
but it must be intentional, remain within validated envelopes, and be reflected in synchronized
documentation where exact populations are stated.

The validator is a gate, not a license-compliance oracle. A passing hash and complete fields cannot
make an incompatible license acceptable; human review remains required before asset adoption.
