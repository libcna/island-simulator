# Mesa recorder readiness audit

Date: 2026-10-09. Related incident: [AMDGPU GPUVM reset](2026-10-08-amdgpu-gpuvm-reset.md).

Follow-up: the exact published Debian revision's nine patches and build rules
are now reviewed in [the distribution patch-scope audit](debian-mesa-patch-audit.md).
None changes the reviewed recorder/descriptor paths. This narrows the packaging
uncertainty, but does not establish binary equivalence or qualify the recorder.

## Decision

Do not launch another hardware reproduction merely with `GALLIUM_DDEBUG` enabled.
The inspected recorder is useful, but it is not a verified, bounded, durable pre-fault
capture of every descriptor needed for this incident. No debugger option was enabled
and no GPU workload was launched during this audit. The hardware stop latch remains active.

The read-only checkout `/home/robertvokac/deps/mesa` is clean at tag `mesa-25.0.7`.
Locations below are relative to that checkout, not files to modify in this project.
An offline `strings` inspection of the installed

successful runtime activation. No application was started to obtain these strings.

## What the code can retain

- `src/gallium/auxiliary/driver_ddebug/dd_screen.c:121` requests
  `PIPE_CONTEXT_DEBUG`. `dd_context.c:965` attaches the context log to the driver.
- `src/gallium/drivers/radeonsi/si_state_draw.cpp:2396` logs graphics state after
  draw-packet emission when a saved command stream exists.
- `si_debug.c:1039` records framebuffer, graphics shaders and internal/shader
  descriptor lists. `si_dump_descriptor_list` at line 716 copies the CPU descriptor
  values, retains a reference to their buffer, and stores its mapped GPU-list pointer.
  The printer at line 647 compares mapped descriptors with the copied CPU values.
- `si_debug.c:456` retains the relevant saved command stream and dword range.
  `si_save_cs` at line 34 copies command chunks and optionally the buffer list.
  The printer uses saved IB bytes once flushed; otherwise it reads the current
  command buffer (`si_log_chunk_type_cs_print`, line 405).

These are substantially more useful than a kernel ring containing only references
to absent userspace indirect buffers. They still require verification in the actual
installed driver before being treated as complete evidence.

## Why this is not a ready pre-fault recorder

1. **Asynchronous disk output.** `dd_after_draw_async` (`dd_draw.c:1237`) creates
   the log page and signals driver completion. A separate `:ddbg` thread then
   writes records via `dd_maybe_dump_record` (line 982). With the default positive
   timeout it first waits for the youngest queued draw's driver and GPU fences
   (line 1135). The files are not synchronously persisted before GPU submission.
   Our first-fault supervisor can terminate the process before the relevant record
   is written. This is a source-level timing concern, not an observed lost recording.
2. **Zero timeout is not a durability guarantee.** Setting timeout zero removes
   GPU-fence hang detection, but the worker still waits for driver completion and
   writes asynchronously. It is not proof of safe current-command-buffer access or
   complete capture before a fault. Do not prescribe it as a verified remedy.
3. **Vertex descriptor coverage is incomplete as currently demonstrated.**
   `si_upload_and_prefetch_VB_descriptors` (`si_state_draw.cpp:1815`) emits some
   vertex descriptors directly into shader registers and uploads the remainder
   through `const_uploader`. The latter go through a separate path explicitly
   outside `si_upload_graphics_shader_descriptors`. The reviewed
   `si_log_draw_state` / `si_dump_descriptors` paths do not explicitly snapshot
   this separate vertex descriptor upload. Register-emitted values may be present
   in the IB, but a pointer to the uploaded remainder is not its payload.
   Gallium's vertex-buffer state dump is not equivalent to those generated bytes.
   This is an evidence gap, not a finding that vertex fetch caused this fault.
4. **Lifetime and timing change.** Debug state copies retain resource references
   (`dd_draw.c:857` and `si_debug.c:752`). Positive-timeout monitoring adds fences;
   `flush` changes submission boundaries. A clean debug run cannot on its own rule
   out a resource-lifetime or scheduling defect in the uninstrumented run.
5. **No verified output bound.** `always` opens one file per dumped record in
   `$HOME/ddebug_dumps` (`dd_draw.c:44,982`). The inspected dump predicate does not
   consult `skip_count`; uses of that member elsewhere gate flushing and progress
   messages. Despite the help text, do not rely on `GALLIUM_DDEBUG_SKIP` to bound
   disk output without checking the installed implementation. No end-count or byte
   cap was identified in this path. Do not repurpose `HOME` to redirect output.
6. **Hang diagnostics have additional side effects.** The hang path invokes
   device-status reporting, including external `umr -O halt_waves` commands through
   `si_dump_debug_state` (`si_debug.c:1023`). This path must not be casually enabled
   on the desktop's GPU.

## Next diagnostic work, without hardware execution

The [capture evidence inventory](capture-evidence-inventory.md) now maps retained
artifacts to the missing per-fault fields and makes the next-run acceptance gate
explicit. It does not qualify this recorder or authorize a hardware run.

1. Debian patch-scope comparison is complete as described above; full orig-source
   and installed-binary equivalence remains unverified. The patch series adds no
   identified remedy for recorder scheduling, output selection or descriptor capture.
2. Establish an evidence inventory for a candidate capture: flushed IB dwords,
   register descriptors, uploaded vertex descriptors, shader descriptors, buffer
   virtual-address ranges, draw identity and process/build identity. Mark missing
   fields explicitly rather than treating an API trace as a complete GPU trace.
3. Verify a bounded capture mechanism and artifact retention before requesting a
   supervised hardware experiment. Preserve a historical executable/source identity;
   a newly polished game build is not the original reproducer.

If these requirements cannot be met with supported diagnostics, prepare an upstream
Mesa/AMDGPU report from the existing evidence instead of inducing another reset.
Do not modify CNA or Sharp Runtime. This audit neither identifies the primary defect
nor qualifies any renderer as fixed.
